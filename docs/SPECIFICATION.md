# welink-sales — Functional & Technical Specification

**Project:** WeLink Sales — invoicing / ERP application (replacement for `laraforma`)
**Status:** Draft for approval — do not build until authorized
**Companion:** `docs/PLAN.md`

---

## 1. Purpose

Rebuild the company's invoicing application as a **clean, supported, hardened Laravel
application**. The replacement is functionally equivalent to the old `laraforma` app (so
staff keep their workflow and historical data), but it is built from scratch on a current
framework/PHP version and **removes every defect that let the site get compromised**.

This document is the source of truth for *what* we build. `PLAN.md` describes *how*.

---

## 2. Context — why this rebuild exists

The old app (`sales.welink.co.tz`, Laravel 8.40 / Livewire 2.4 / PHP 7.3–8.0) was the
**primary entry point** for the 2024–2026 compromise of `welink.co.tz`. The confirmed root
causes (from `ATTACK-VECTOR-REPORT.md`, `IOC-ATTRIBUTION-ADDENDUM.md`):

| # | Defect | Consequence |
|---|--------|-------------|
| 1 | `EnsureEverythingIsOkay` seed controller left in production, auth middleware **commented out**, hardcoded super-admin (`aemmanuel199@gmail.com`, password == email) | Credentialless account takeover |
| 2 | `OnlineTerminal` Livewire component running `shell_exec($this->command)` | Remote OS code execution |
| 3 | `User` does **not** implement `MustVerifyEmail` while routes use `verified` | Email-verification bypass |
| 4 | RBAC "abilities" defined but **not enforced** in components/controllers | Any logged-in user can do anything |
| 5 | Laravel 8.40 + Livewire 2.4 + PHP 7.x — all end-of-life | Known CVEs, no security patches |
| 6 | Hardcoded credentials in `.env` (DB, SMTP, `APP_KEY`) | Credential reuse / leakage |
| 7 | App obtained as an unverified/nulled build (`support@laraforma.gq` super-admin) | Supply-chain backdoor risk |

**Critical additional finding during this analysis:** the "cleaned" `public_html/laraforma`
copy still contains **four active `.log`-disguised backdoors** (the `@eval(file_get_contents(...))`
family, C2 `s.newnday.xyz`):

- `resources/views/settingsWHalLtrYVodZ.log`
- `database/seedersZMKTr.log`
- `app/HttpmlavpePwGDZL.log`
- `storage/debugbarcefWC.log`

Therefore the new app **must be scaffolded fresh** and its `vendor/` regenerated by
`composer install` from packagist — **never** copied or reused from the compromised tree.

## 3. Target stack

| Layer | Choice | Notes |
|-------|--------|-------|
| PHP | **8.3** (floor 8.2, tested through 8.5) | Local dev is 8.3.31. Replaces the old `^7.3\|^8.0`. |
| Framework | **Laravel 12** (primary) or Laravel 13 | Both require PHP ≥8.2/8.3 and carry active security support. See §3.1. |
| Livewire | **3.x** | Replaces Livewire 2.4. |
| Auth | Laravel built-in session auth + `MustVerifyEmail` | Registration disabled (matches old app). |
| Frontend | **Bootstrap 5 + AdminLTE 4** | Natural successor to Bootstrap 4 + AdminLTE 3; preserves staff UX. |
| PDF | `barryvdh/laravel-dompdf` (^3) | Invoice / proforma / LPO / delivery-note PDFs. |
| Database | MySQL 8.x (utf8mb4) | Existing data import target. |
| Build assets | Vite (Laravel 11/12 default) | Replaces Laravel Mix / webpack. |

Packages from the old app that are **removed** (now built into Laravel or obsolete):
`laravel/ui`, `fideloper/proxy`, `fruitcake/laravel-cors`, `facade/ignition`
(superseded by `laravel/error-solutions`), `webpack.mix.js`.

### 3.1 Framework support (source: [Laravel release notes](https://raw.githubusercontent.com/laravel/docs/refs/heads/12.x/releases.md))

| Laravel | PHP | Security fixes until |
|---------|-----|----------------------|
| 8 (old app) | 7.3–8.0 | EOL (years ago) |
| 11 | 8.2–8.4 | 12 Mar 2026 |
| **12** | **8.2–8.5** | **24 Feb 2027** |
| 13 | 8.3–8.5 | Q1 2028 |

**Decision:** build on **Laravel 12 / PHP 8.3** (most stable current line, minimal breaking
changes, easiest to keep current). Laravel 13 is a drop-in forward target if we want the
longest support window (Q1 2028) — confirm at scaffold time; the architecture is identical
either way.

## 4. Functional scope (feature parity with `laraforma`)

The app is a **Tanzanian IT/telecom contractor's sales + light-ERP system**. Modules, in
build order (see PLAN.md):

1. **Authentication & user management** — login/logout, email verification, password
   reset/change, user CRUD (with `super` flag, role assignment, active/inactive, theme).
2. **Roles & permissions (RBAC)** — roles, the 76 existing abilities, role→ability and
   user→role pivots. **Enforced** this time (see §6).
3. **Master data** — customers, suppliers, items + item categories, currencies (multi-rate),
   internet packages.
4. **Documents** — the core of the app:
   - **Proformas** (quotes) → convertible to invoices.
   - **Invoices** (with advance, discount, VAT, withholding tax, labor charge, exchange rate).
   - **Delivery notes** (linked to an invoice; line items carry serial numbers).
   - **Local Purchase Orders (LPOs)** (linked to suppliers).
5. **Internet/ISP billing** — internet customers (linked to a base customer + package),
   recurring internet invoices with `effective_from`/`effective_to` and package line items.
6. **Accounts** — income accounts, expense accounts, expense recording (receipt upload,
   narration, project + account links).
7. **Projects** — project CRUD with manager, customer, estimated budget/time, status
   timeline, file attachments.
8. **Settings** — key/value settings (VAT %, withholding-tax %, print items-per-page) with
   an audit changelog.
9. **Dashboard** — summary cards, income chart, recent projects.
10. **Output** — PDF generation for proforma / invoice / LPO / delivery note; due-invoice
    reminder emails (customer + office).

### 4.1 Document numbering conventions (preserved)

| Document | Prefix | Old generator (buggy) → new service |
|----------|--------|-------------------------------------|
| Invoice | `WE/INV/No:N` | `DocumentNumberService` |
| Proforma | `WE/PF/No:N` | `DocumentNumberService` |
| LPO | `WE/LPO/No:N` | `DocumentNumberService` |
| Internet invoice | `WE/INTERNET/INV/No:N` | `DocumentNumberService` |

The old helpers (`app/CustomHelpers.php`) had off-by-one substring bugs and a duplicated
`user()` definition; these are replaced by testable services.

## 5. Data model

The new schema is produced by **proper Laravel migrations** and is **compatible with the
existing cleaned database dump** (`db-backups-clean/welinkco_laraforma.sql`) so historical
data imports without transformation. 32 tables, the same set as the old app:

**Identity / RBAC**
- `users` — `id, created_by, updated_by, name, email (unique), email_verified_at, super,
  active, theme, password, remember_token, timestamps`. *(Old profile fields
  `passport/education/location/skills/notes` are optional; kept only if the UI uses them —
  see decisions §9.)*
- `roles`, `abilities`, `role_user` (`user_id, role_id, created_by`),
  `ability_role` (`role_id, ability_id, created_by`).

**Master data**
- `customers` — `name, postal_code, postal_address, location, contact, tin, vrn, status`.
- `suppliers` — `name, location, contacts, postal_code, postal_address, tin, vrn, status`.
- `item_categories` — `name, description, active`.
- `items` — `category_id, name, unit_measure, specification, price, active, vat`.
- `currencies` — `code, name, rate, active`.
- `packages` — `name, description, price, status` (ISP packages).

**Documents**
- `proformas` + `proforma_items` — header (`name, postal, location, contact, date, notes,
  for, advance, currency, exchange_rate, labor_charge, vat, withholding_tax, tin, vrn`)
  and line items (`item_id, specification, unit_measure, quantity, price`).
- `invoices` + `invoice_items` — as proforma plus `proforma_id` (conversion link),
  `discount`; items carry `price`.
- `delivery_notes` + `delivery_note_items` — `invoice_id, date, name, postal, location,
  contact, tin, vrn`; items carry `serial_no`.
- `local_purchase_orders` + `local_purchase_order_items` — `supplier_id, date,
  reference_no, currency, for, proforma_referenced, extra_notes, vat, withholding_tax, status`.

**Internet billing**
- `internet_customers` — `customer_id, package_id, started, status`.
- `internet_invoices` — `customer_id, reference, date, effective_from, effective_to, vat,
  currency, status`.
- `internet_invoice_packages` — `invoice_id, package_id, description, quantity, unit_price`.

**Accounts / projects / settings**
- `income_accounts`, `expense_accounts` — `name, description, active`.
- `expenses` — `requested_by, expense_account_id, income_account_id, project_id,
  receipt_number, amount, narration, receipt (path)`.
- `projects` — `manager, customer_id, name, starts_on, estimated_budget, estimated_time
  (days), description`.
- `project_statuses` — `project_id, status (on hold|canceled|completed|progressing|pending),
  comment`.
- `project_files` — `project_id, name, file`.
- `settings` — `name, value`; `setting_changelog` — `updated_by, setting_id, from, to`.

### 5.1 Schema improvements over the legacy schema

- Add **`ON DELETE` behaviours** that match intent (e.g. cascade document line items;
  `SET NULL`/restrict on user FKs where history must survive account deletion).
- Add **indexes** on frequent query columns (document dates, references, statuses).
- Use `decimal(25,2)` for all money (already largely correct) — no `float`/`double` for
  amounts in new code.
- Introduce **soft deletes** where staff expect "undelete" (customers, items, documents) —
  decided per module; the RBAC `remove` abilities map to soft delete where chosen.
- Keep the same table names so the cleaned dump imports 1:1.

## 6. Security requirements (non-negotiable)

Every requirement below maps directly to an incident root cause. The app is not "done"
until each is verified.

1. **No remote code execution surface.** No `shell_exec`, `exec`, `system`, `passthru`,
   `proc_open`, `popen`, `eval`, or `assert` anywhere in app code. `OnlineTerminal` and
   `EnsureEverythingIsOkay` are **not recreated**. Host `php.ini` keeps `disable_functions`
   for these.
2. **No hardcoded credentials.** All secrets come from `.env` (gitignored) and a proper
   secret/vault at deploy time. `APP_KEY` generated via `php artisan key:generate`. Admin
   accounts are created by a **guarded seeder** that requires an explicit, randomly
   generated password passed via environment — never a fixed value.
3. **Email verification enforced.** `User implements MustVerifyEmail`; all app routes sit
   behind `auth` + `verified`.
4. **Registration disabled** (`register => false`), matching the old app's intent.
5. **Authorization actually enforced.** RBAC abilities are checked in every Livewire
   component / controller via a policy or `Gate` + an `ability` middleware. The `super`
   flag bypasses. The old app *defined* abilities but never enforced them — this is fixed.
6. **Input validation & mass-assignment.** Every Livewire property validated with
   Livewire 3 `#[Validate]`/`->validate()`; models use `$fillable` allow-lists only
   (no `$guarded = []`); no `request()->all()` mass assignment.
7. **CSRF / XSS / SQLi.** Blade auto-escaping, Livewire 3's signed-request handling, and
   Eloquent parameter binding are used throughout; no raw SQL string concatenation with user
   input.
8. **File uploads hardened.** Receipt and project-file uploads restricted to an allow-list of
   MIME types, size-capped, randomly named, stored outside the web root or in a
   non-executable storage path, and validated (never `.php`/`.log`).
9. **Session & rate limiting.** Login throttling (`ThrottleRequests`), logout on password
   change, session fixation protection (default), and password-confirmation for sensitive
   actions (delete, role changes).
10. **Secure defaults.** `APP_DEBUG=false` in prod, HTTPS-only cookies, sane
    `SESSION_SECURE_COOKIE`, and no `.env` exposure.
11. **Dependency hygiene.** `composer.lock` committed; dependencies on supported versions;
    `composer audit` in CI to catch known CVEs.
12. **Isolation (deploy).** The app runs under its own OS user/container, separate from the
    WordPress site, so one compromise cannot reach the other (see PLAN.md §Deployment).

### 6.1 What is intentionally out of scope for v1 (can be added later)

- Two-factor authentication (recommended as a fast-follow; Loginizer-equivalent for the app).
- Full audit log of every entity mutation (currently only `settings` have a changelog).
- Tenant/multi-company separation.

## 7. Non-functional requirements

- **Compatibility:** PHP 8.2–8.5; MySQL 8.0; runs under Apache/Nginx with `disable_functions`
  still enabled.
- **Data preservation:** all historical records (customers, 437 proformas, 240 invoices, LPOs,
  delivery notes, items, projects, expenses, settings) import cleanly.
- **Usability:** staff workflow is unchanged from `laraforma` (same screens, same printouts,
  same reference numbers).
- **Testability:** unit tests for numbering/tax/currency logic; feature tests for auth/RBAC
  and each document's create→print flow.
- **Performance:** paginated lists, indexed lookups; PDF generation off the request path if
  large batches become slow.

## 8. Data migration strategy

1. Export a fresh, **verified-clean** copy of `welinkco_laraforma` (the cleaned dump in
   `db-backups-clean/` is the starting point).
2. **Delete rogue accounts** before/at import: `aemmanuel199@gmail.com`,
   `support@laraforma.gq`, and any user with `super=1` that staff cannot verify. Rotate all
   user passwords.
3. Run the new migrations against an empty database, then import data table-by-table in
   dependency order (abilities → roles → pivots → users → master data → documents → items →
   accounts/projects/settings).
4. Re-seed `abilities` (the 76 names) and `settings` (VAT `18`, withholding tax `2`,
   print-items-per-page `10`) from the dump data, and create the first legitimate admin.
5. Verify counts match the source dump and spot-check a proforma/invoice PDF renders the
   same values.

## 9. Open decisions to confirm before/at build start

1. **Framework minor:** Laravel 12 vs 13 (both fine; 13 has the longest support window).
2. **Admin UI look:** AdminLTE 4 (recommended, familiar) vs a fresh Bootstrap 5 layout vs
   Tailwind + Livewire 3 starter kit.
3. **Legacy user profile fields** (`passport`, `education`, `location`, `skills`, `notes`)
   and `CustomHelpers` niceties (`formatTIN`, `formatVRN`, `datey`) — keep or drop.
4. **Soft deletes:** adopt everywhere, or only where staff request undelete.
5. **2FA / audit log** — fast-follow vs part of v1.

These are captured so we can answer them at the start of Phase 1 rather than mid-build.
